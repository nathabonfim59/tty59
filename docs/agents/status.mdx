tty59 uses the foreground process to identify an agent, then reads its status
from hooks, terminal titles and progress sequences, and visible terminal text.
This can distinguish a working agent from one waiting for you to answer a
question or approve an action.

## Installing the hooks

**Settings → Integrations** lists every agent that can report status, with an
**Install** button beside each:

| Agent | |
|---|---|
| Claude Code · Codex · TraeCode · Copilot CLI · OpenCode · Pi · Grok Build · Oh My Pi · Gemini · Droid · Qwen Code · Goose · Kimi Code · Qoder CLI · Qoder CN CLI · Crush · CodeBuddy · Cursor CLI · Prime Agent · Antigravity · Empryo · Muse Code · jcode | Hooks available |
| Aider · Amp · Auggie · Hermes · Vibe | No hooks. Amp and Hermes can report status through their terminal UI. |

Installing writes into that agent's own configuration directory. Once installed
the row grows a second **Uninstall** button beside the first, which itself
becomes **Reinstall** — or **Update**, against an **Outdated** state, when tty59
ships a newer hook.

<Note>
  Crush ships only a `PreToolUse` hook today. It is enough to remember the
  session for resume, but there is no turn boundary behind it, so a Crush pane
  carries no status dot and `tty59 wait` times out rather than returning.
</Note>

<Note>
  Antigravity has no permission hook. When tty59 has its live terminal screen,
  it can still recognize a permission or question dialog. Antigravity's hooks
  live in a `tty59` set inside `~/.gemini/config/hooks.json`.
</Note>

<Note>
  `cursor-agent -p` (print mode) sends neither of Cursor's turn hooks, so a
  headless run records its session id — Copy Session ID and resume still
  work — but shows no status dot. The interactive `cursor-agent` shows the
  full working → done cycle.
</Note>

<Note>
  The hooks only do anything inside tty59. Running the same agent in another
  terminal is unaffected.
</Note>

Hooks are installed per machine. Once a second
[machine](/remote/workspaces) is linked, a row of chips appears above the table
to pick which one you are looking at, and the table then shows that machine's
agents — so a dev box gets its hooks installed the same way, from the same
screen.

## The status dot

Screen detection runs on live desktop grids, including background tabs and
remote workspace panes opened on the desktop. Sleeping panes and panes whose
grid isn't open in a desktop window rely on the available hook, title and
progress signals. Older remote servers do not receive screen evidence.

Every tab chip and sidebar row carries a dot:

| Dot | Meaning |
|---|---|
| 🔵 **Blue** | Working |
| 🟠 **Amber** | Needs your input — a permission prompt, a question |
| 🟢 **Green** | Done with this turn |

<Frame caption="Working (blue), waiting on you (amber), and done (green), side by side">
  <img src="/images/agent-status.webp" alt="Agent status dots" />
</Frame>

The same three states are what `tty59 agents` reports as `working` / `waiting` /
`done`, and what [`tty59 wait`](/agents/orchestration) blocks on. A fourth state,
`idle`, carries no dot — it is an agent that has not started a turn.
After the agent process exits, the terminal can stay open at the shell. New
clients identify that agent as exited; older clients read the status as idle.

## Notifications

Two, both following your **Settings → General → Notifications** policy:

- **"needs your permission…"** the moment an agent blocks on you
- **"finished after 42s"** at the end of a turn

Which means that by default — *When unfocused* — you are told the instant you
are the bottleneck, and left alone while you are watching.

A program can also post its own notification with OSC 9, OSC 777
(`notify;title;body`) or kitty's OSC 99. tty59 shows it under the same policy,
held back only while you are looking at that pane, and a click reveals the
pane. Claude Code writes one when its **Notifications** setting (`/config`) is
`ghostty`, `kitty` or `iterm2`. Its default, `auto`, sends nothing in tty59. A
pane whose agent already reports through tty59's hooks skips the copy that would
repeat the notice above.

## The tray icon

tty59 keeps a status item in the system tray (menu bar on macOS). It flips to an
attention state the moment *any* agent anywhere needs input, so you can see it
without the window in front of you.

Its menu lists every agent pane with its brand avatar and status dot — click one
to reveal it — and also holds the notification policy switch and **Quit and Stop
Server…**. An agent that needs input says for how long (*needs input · waiting
3m*), and the workspace switcher shows the same age beside its tab.

## Jumping to the agent that needs you

**Agent: Go to Next Needing Attention** (<kbd>⌘ ⇧ U</kbd>, <kbd>Ctrl ⇧ U</kbd>
on Windows and Linux; `FocusNextAgentNeedingAttention` to rebind) reveals the
agent pane that has been waiting on you longest, switching tab or window to get
there. It looks at the tabs open in your windows, the same agents the tray menu
lists; a workspace no window is showing is left out. Press it again for the next
one: every waiting agent, oldest first, then each finished turn you have not
looked at yet, and round again. With nothing waiting it says so and stays where
you are. Each wait is timed by the clock of the machine the agent runs on, so
agents on machines whose clocks disagree can show ages, and queue, slightly off.

Turn it off with **Settings → General → Show tray icon**
(`show_tray_icon: false`).

## Inbox and Kanban

The **Agents (n)** button in the terminal area's top bar opens the agent Inbox.
The count is the number of agents needing attention in the current workspace.
Use **Workbench** to return, or toggle with <kbd>⌘ ⇧ Y</kbd> / <kbd>Ctrl ⇧ Y</kbd>
(`ToggleAgentVision`). **Settings → General → Start windows in agent mode**
opens new windows in the Inbox; Workbench is the default.

The projects column uses the current workspace's existing sidebar groups.
**All in workspace** clears the project filter. The normal workspace switcher
and <kbd>⌘ ⇧ O</kbd> / <kbd>Ctrl ⇧ O</kbd> work here too. **Search agents…**
filters by title, agent kind, project and reason in both Inbox and Kanban.

Each entry is one agent pane. Split tabs show a **pane i/n** marker, and the
reading pane contains only that pane's live terminal. Plain shells and editors
do not appear. Waiting agents come first, then finished turns you have not seen;
**Other agents** expands the working, idle, handled and exited entries.

While the list has focus, use <kbd>↑</kbd>/<kbd>↓</kbd> or <kbd>j</kbd>/<kbd>k</kbd>
to select and <kbd>Enter</kbd> to answer in the terminal. <kbd>Esc</kbd> returns
to the list. <kbd>[</kbd>/<kbd>]</kbd> changes project. Search keeps these plain
keys for typing; <kbd>Down</kbd> or <kbd>Enter</kbd> moves from search to the list.

In agent mode, **Next needing attention** (<kbd>⌘ ⇧ U</kbd> / <kbd>Ctrl ⇧ U</kbd>)
marks the current event handled and focuses the next agent in this workspace.
It can clear the project/search filter to reach that agent. With nobody else
needing you, it stays put. **Mark handled** uses <kbd>⌘ ⌥ ⇧ U</kbd> /
<kbd>Ctrl Alt ⇧ U</kbd>. Handling affects read state; the status dot continues
to show the agent's actual status. A new attention event makes it unread again.

**Kanban** groups the same agents into Waiting, Working, Done, Idle and Exited.
Use <kbd>←</kbd>/<kbd>→</kbd> or <kbd>h</kbd>/<kbd>l</kbd> to change columns and
<kbd>↑</kbd>/<kbd>↓</kbd> or <kbd>j</kbd>/<kbd>k</kbd> to select a card.
<kbd>Enter</kbd> opens its terminal in the Inbox. Toggle Inbox/Kanban with
<kbd>⌘ ⌥ ⇧ Y</kbd> / <kbd>Ctrl Alt ⇧ Y</kbd> (`ToggleAgentBoard`).

## Sending an agent some context

Two Search Everywhere actions hand what is in front of you to the agent running in
the pane, as a ready-made prompt:

| Command | Sends |
|---|---|
| **Agent: Send Selection** | The current terminal selection |
| **Agent: Send Git Diff for Review** | The repository's `git diff` |

If nothing recognisable is running, tty59 says *"No running coding agent found"*
rather than typing into your shell.
