The CLI is only half of the story. An agent has to know *when* reaching for a
pane beats running a command, and — more importantly — which panes it must not
touch. That is what the skill is for.

## Installing it

The skill is built into the `tty59` binary, so it always matches the CLI you
have:

```bash
tty59 skill install                 # ~/.claude/skills/tty59
tty59 skill install --agent agents  # ~/.agents/skills/tty59 (Codex, OpenCode, …)
tty59 skill install --dir ./skills  # anywhere else
```

Run it again after upgrading tty59. It replaces what it wrote before. It never
overwrites a `tty59` skill you wrote yourself: `--force` moves yours to
`tty59.bak-<time>` and installs beside it.

It is also published from the repository:

```bash
npx skills add nathabonfim59/tty59
```

The source lives at
[`skills/tty59/`](https://github.com/nathabonfim59/tty59/tree/main/skills/tty59) in the
repository: a `SKILL.md` and two references — the full command table, and a
delegation playbook the agent reads before handing work to another agent.

## Agents on a remote machine, VM or container

An agent running in a pane of a [remote workspace](/remote/workspaces) is on a
machine where tty59 installed only `tty59-server`, so the `tty59` CLI is not
there. That binary answers a small set of pane verbs of its own, scoped to the
agent's workspace and sidebar group: `scope`, `ls`, `tab new`, `tab close`,
`split`, `send`, `capture`, `procs`, `wait`, `close`. Run this once on that
machine:

```bash
"$(ls -t ~/.local/share/tty59/bin/tty59-server-c* | head -n 1)" skill install
```

That writes the `tty59-remote` skill and a `scripts/tty59` shim, which finds
the server binary even after an upgrade renames it.

## Panes that are an ssh session

A pane where someone typed `ssh host` is not a remote workspace: tty59 isn't
running on the far end, and its shell usually has no tty59 integration.
`tty59 exec` can't see that shell's prompt or exit code, so it refuses the
pane, names the host and points at `send`. Both skills teach the same fallback:
`send` the command with a marker such as `echo "__done rc=$?"`, then `capture`
until the marker appears. `procs --json` shows which case a pane is in:
`context.remote` is set and `remote_prompt_seen` is false.

## Updating it

If you installed it with `tty59 skill install`, run that again. With `npx`,
`add` does not refresh a skill that is already installed. Updating is a
separate command, and the skill is named `tty59`:

```bash
npx skills update tty59    # this one
npx skills update         # everything you have installed
```

The CLI records where each skill came from, so `update` re-downloads only what
has drifted. `npx skills remove tty59` takes it back out.

## What it teaches

### When to use a pane instead of a plain command

The Bash-style tool an agent already has is right for anything that starts, does
its job, and exits. A pane is right when:

- **It should not block.** A dev server, a watcher, `tail -f`, a long test run.
- **It is interactive or stateful.** A REPL, `ssh`, a database shell — anything
  where you send, read, then send again. A pane keeps the session alive between
  turns; a one-shot call cannot.
- **It needs a real TTY.** Programs that detect a pipe and change behaviour —
  colour, progress bars, TUIs, `top`, raw mode.
- **The user should be able to watch.** Anything in a pane shows up live in
  their window. That is often the whole point.
- **You are being asked about something you did not start.** "What's running in
  that pane?", "why is port 3000 taken?", "what are my agents doing?"

### The safety rules

<Warning>
  The panes on this machine are the user's real work, and some of them are other
  coding agents mid-task. Anything the agent did not create is read-only.
</Warning>

- **Never `send` into a pane you did not open.** Keystrokes land in the middle
  of whatever is happening there. Check `tty59 agents` first.
- **Never close a pane, tab, or workspace you did not create.**
- **Never `server stop` or `server restart`.** Every pane on the machine dies
  with the server, including yours.
- **Never `tty59 server start` on your own initiative** when `doctor` says the
  server is unreachable — starting one the user did not ask for changes what
  their GUI attaches to. Tell them instead.
- **Clean up what you did create.** `tty59 pane close %83` when the scratch pane
  is done with.

### The reliable idioms

Rather than screen-scraping, the skill points agents at the primitives that
actually answer the question:

```bash
# is it finished? — when only the depth-0 shell is left, yes
tty59 procs %83 --json

# the answer, not the view
tty59 send "$PANE" 'cargo test > /tmp/t.log 2>&1; echo $? > /tmp/t.rc' --enter

# wake up exactly when the other agent needs something
tty59 wait %3 --until waiting,done --changed --timeout 600
```

### How to delegate

`references/delegation.md` is the part the agent reads before spawning a
worker: give the worker its own git worktree and workspace, hand the task over
in interactive mode with the delivery contract in the prompt, prove the
command actually started, babysit with `tty59 wait`, collect the result out of
git rather than the screen, clean up — and, for a fan-out, harvest with short
per-worker timeouts so one stuck worker cannot stall the round.
